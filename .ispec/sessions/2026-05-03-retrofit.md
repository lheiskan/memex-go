## Trigger

Adopting ispec on memex-go right after the initial drop-in
reimplementation landed. Two commits, ~2,400 LOC, no prior docs —
the codebase exists but its load-bearing decisions live only in
this conversation's context. Capturing them as canon now (while the
"why" is fresh) is much cheaper than retroactively reverse-engineering
later.

## Scope

Narrow / minimum-viable, per the user's instruction: 1 stakeholder, 5
ADRs (the load-bearing decisions are dense for a 2400-line port), 2
requirements, 6 features, 1 spec section. 16 cards total.

## Reading phase

Inputs already in conversation context (no fresh reads needed):

- The full Go source (`card/`, `search/`, `graph/`, `sync/`, `mcp/`,
  `cmd/memex/`).
- The full upstream JS reference at
  `/opt/homebrew/lib/node_modules/@touchskyer/memex/dist/`, which
  this port mirrors.
- The conversation thread itself (motivation, library choice
  rationale, omitted-features rationale, smoke test results).

The manic retrofit at `~/src/manic/.ispec/` was used as the structural
template (stakeholder / ADR / requirement / feature / spec card
shapes, frontmatter fields, lint expectations).

## Discoveries during reading

- The `source` frontmatter field is overloaded in the upstream tool —
  sometimes a client tag (`claude-code`), sometimes an operation tag
  (`retro`, `organize`). Captured as a "Source field overloading"
  note in [[SPEC-domain-model]] rather than fixing it, to preserve
  drop-in compatibility.

- The legacy `Thu Apr 16 2026 ...` date string format in some of the
  user's cards is a real bug surface for `--since` / `--before`
  filters. Carried forward as-is in the port; flagged in [[F-2]] for
  a future fix.

- ispec's session-card `affected_cards` field uses stable IDs
  (`STK-1`, `ADR-0001`, etc.), but cross-card references in prose
  use wikilinks (`[[F-1]]`). Both forms coexist; lint should validate
  both — assumed working until proven otherwise.

- The retrofit was batched (cards drafted in groups by type) rather
  than one-at-a-time per the skill's guidance, following the precedent
  set by manic's retrofit and per the user's auto-mode operating
  preference.

## What's deliberately NOT being captured

- A spec section per package (search, graph, sync, mcp, cli). The
  feature cards already cover each surface; an additional spec layer
  isn't load-bearing for a project this small. If the codebase grows
  past one author or one machine, spec sections per subsystem become
  worth the cost.

- Per-tool MCP schemas as ADRs. The 10 tool schemas are documented in
  [[F-4]] and live in `mcp/server.go`; the schemas themselves don't
  rise to "decision worth canon."

- Retroactive feature cards for sub-features of upstream that we
  *didn't* implement (semantic search providers, the share-card UI,
  the timeline graph view). Their absence is documented in
  [[ADR-0005]]; cards for hypothetical future work would be premature.

- Test infrastructure as a feature. The round-trip test in
  `card/parser_test.go` is documented as part of [[F-1]]'s
  verification section, not a separate card.
